## 一、小猫是什么

> **小猫是我的个人项目进度秘书。**
> 它每天主动告诉我：做了什么、多了哪些核心功能、做到哪了、代码在哪（只在本机，还是已经推到 GitHub）。开工时，它告诉我从哪继续。
> 它不替我写代码，也不替我派活。

用户的三个使用时刻：

| 时刻 | 小猫给什么 | 好不好的标准 |
| --- | --- | --- |
| 早上开工 | 昨天停在哪、哪些东西还没提交或推送、建议先做什么 | 看一眼就知道打开哪个项目 |
| 晚上收工 | 今天推进了哪些核心功能，每条标出代码在哪 | 2 分钟读完，不需要查词 |
| 每周日 | 各项目本周新增了哪些核心功能 | 能看出项目在往前走 |

另有一项随时可用的能力：**继续卡片**。对某个项目要一张 5 行卡片，直接贴给 Claude Code 或 Codex 当开场白。

## 二、四档状态：代码在哪

**每一条变化都必须带下面四个标签之一。** 这是用户最需要、而当前日报完全缺失的信息。当前日报只能写「已提交；合并和正式启用未核实」，原因是采集层从不读取远端分支信息。

| 标签 | 意思 | 判定方法（全部只读） |
| --- | --- | --- |
| 🟡 未提交 | 改了，还没 commit | 工作树 dirty（现有采集已有） |
| 🟠 仅本机 | commit 了，还没推送 | 提交不是任何 `refs/remotes/*` 的祖先 |
| 🔵 已推送 | 推到 GitHub 了，还没合进 main | 是某个远端分支的祖先，但不是远端默认分支的祖先 |
| 🟢 已合并 | 已经在 GitHub 的 main 里 | 是 `origin/<默认分支>` 的祖先 |

- 用到的 git 命令：`for-each-ref refs/remotes`、`merge-base --is-ancestor`、`symbolic-ref refs/remotes/origin/HEAD`。都通过现有 `git_readonly.run_git` 执行，不 fetch、不写业务仓。
- 没有 remote 的项目只显示前两档，并在项目名后标「（无远端）」。
- 「已上线 / 已部署」不在本方案范围内；需要时另加，不能从 Git 状态推断。

### 两台机器

用户在 **Mac Studio**（小猫运行在这里）和 **MacBook Pro** 上都会写代码，两边通过 GitHub 同步。

问题：小猫只看 Mac Studio 的磁盘。MacBook 上推到 GitHub 的提交，如果 Mac Studio 没有 pull，小猫就看不到。另外，Mac Studio 本地的 `refs/remotes/*` 只在 push 或 fetch 时更新，所以有可能已经过时。

方案：**小猫在自己的数据目录里，为每个有 remote 的项目维护一份 bare 镜像。**

```
~/Library/Application Support/Xiaomao/mirrors/<project_id>.git
```

- 每 30 分钟对镜像执行一次 `git fetch --prune`。只写小猫自己的目录，业务仓仍然不 fetch、不写。
- 有了镜像，四档判定就改为以镜像的分支为准，不再依赖本机过时的 `refs/remotes`。
- 镜像里有、本机仓库里没有的新提交，标为「💻 来自另一台机器」，并照样归入功能。
- fetch 失败（离线、没有认证）不影响日报。只在日报末尾加一行「GitHub 状态未更新（上次成功：时间）」。
- **已知局限**：MacBook 上**没推送**的工作，小猫看不到。日报末尾固定提示一句。以后如有需要，可以在 MacBook 上跑一个只扫描、不出报告的轻量小猫，这一点不在当前阶段。

## 三、晚报长什么样

### 写作规则（所有给用户看的文字都适用）

1. 第一行用一句话说清今天，例如：今天 3 个项目有进展，2 处代码还没推送。
2. 最多 3 个项目，每个项目最多 3 条**核心功能**。用「现在能做什么了」的口吻来写，不出现类名或函数名。
3. 每条都带四档状态标签。
4. 「明天从这里继续」：2–3 条，由规则生成，模型只负责润色。
5. 没有变化的项目合并成一行。
6. 采集问题、截断、脱敏、模型缺失等技术细节合成**一行**，例如「3 处采集问题，详见依据」，完整内容放进依据文件。
7. 不出现以下用词：未核实、范围哈希、观察 ID、覆盖 partial、功能归属待确认、交付状态待确认。确实不知道时就说「这条看不出具体做了什么」。

### 样例

下面用 10/13 日报的真实内容改写。状态标签**仅作示意**，真实状态要等阶段 1 实现后才能得出。

```
小猫晚报 · 10月13日（周一）
今天 2 个项目有实质进展，xiuqiu-site 有 2 个提交还没推送。

★ Wallet-Infrastructure · 热钱包对账保护
  · 对账出现异常时，签名请求会自动暂停，不会误发上链      🔵 已推送
  · 新增处理对账异常的入口，可以手动或自动恢复            🔵 已推送
  · 系统启动时自动开启对账任务                          🔵 已推送
  （另有 72 处改动还没提交）

★ xiuqiu-site · 简报页面
  · 简报的数据来源可以按类型配置                         🟠 仅本机
  · 没有结果时的提示更清楚，可一键清除筛选               🟢 已合并
  · 主题筛选改用通用组件                                🟢 已合并

· 小猫：只改了文档                                     🟡 未提交

明天从这里继续
  1. xiuqiu-site：推送本地的 2 个提交
  2. Wallet-Infrastructure：72 处未提交改动，建议分批提交
  3. Wallet-Infrastructure：对账分支已推送，还没合进 main

今天没动：QAI、wallet-core、AI-Web3-Learning、旷野之心
3 处采集问题、部分内容未纳入解读 → 菜单「查看依据」
```

### 和现在的区别

| 现在 | 以后 |
| --- | --- |
| 7 个项目全部展开，没动的也占一段 | 只展开有进展的项目，没动的合成一行 |
| 每条都写「已提交；合并和正式启用未核实」 | 每条一个四档标签 |
| 「仍在推进」「待确认与采集缺口」共 30 行 | 合成「明天从这里继续」加一行问题汇总 |
| 「OutboxHandlerConfig 接口」 | 「简报的数据来源可以按类型配置」 |
| 第二天中午才生成 | 21:45 前送达（规则版先发，模型解读后补） |

**依据文件（`daily-evidence`）保持现在的严谨程度不变**。白话晚报只是另一种呈现，证据并没有减少。

## 四、主动汇报

| 什么 | 什么时候 | 通知里直接写什么 | 点开看什么 |
| --- | --- | --- | --- |
| 晚报 | 每天 21:30 窗口结束，21:45 前送达 | 第一行总结 + 第一条「明天从这里继续」 | 白话晚报 |
| 开工提醒 | 每天早上（默认 09:30，可配置） | 「昨天停在：xx；还有 N 处未推送」 | 早报（见下） |
| 未推送提醒 | 本机提交超过 24 小时没推送 | 「xiuqiu-site 有 2 个提交放了 26 小时没推送」 | 继续卡片 |
| 每周进度 | 周日 21:30 晚报之后 | 「本周 4 个项目新增 9 项核心功能」 | 周报 |

- 每一种通知，同一件事每天最多提醒一次。沿用现有 `daily_notifications` 的「先记账再发送」做法。
- 全部可以在 `config.json` 里单独关闭。
- 早报内容：昨天的「明天从这里继续」、各项目的四档计数（未提交 / 仅本机 / 已推送未合并），以及昨晚到现在镜像里新出现的「来自另一台机器」的提交。

### 晚报为什么晚，以及怎么准时

`daily_jobs.run_daily` 当前的顺序是：先采集，再**逐项目调用本地模型**，最后写报告和发通知。模型慢或数据库被锁时，整份日报和通知都会跟着推迟。10/13 的日报到 10/14 11:58（台北）才生成，日志里累计有 440 行 `database is locked`。

改法：
1. 先生成并发出**规则版**晚报（不调用模型），通知随之发送。
2. 模型解读完成后，原地更新同一份晚报，并标注「已补充解读」，不再重复发通知。
3. 先在合成环境中复现 `database is locked`，再做修复。修复前不要预设根因。`store.open_db` 每次打开都会执行 `init_db`，这是首要排查方向。

## 六、项目进度（功能时间线）

晚报里每一条「核心功能」都会存入一张功能时间线表：项目、功能名、日期、状态，状态会随时间更新，比如从仅本机变成已合并。

基于这张表可以做三件事：
- **周报**：各项目本周新增的核心功能，以及当前所处的状态。
- **菜单「项目进度」**：每个项目最近 5 项核心功能。
- **状态自动升级**：同一个功能后来被推送或合并了，时间线上会更新，晚报里也会出现「✅ 上周的 xx 已合并」。

功能名沿用现有的 `feature_daily` 归并结果，以及 `features set` 的手工修正。

## 八、继续保留的原则

- 只读：业务仓不 fetch、不写、不跑测试。镜像只写小猫自己的目录。
- 模型只负责解读和润色，范围、状态、时间都由程序判定。模型失败时保留规则版。
- 只观察登记的个人项目，公司项目不进入。
- 依据文件保持严谨，白话报告负责可读。两者引用同一份数据。
- 改动先在隔离环境验收，切换正式安装由用户确认。

## 十、小猫在小镇里的定位（2026-10-31 用户确认）

小镇是 Session Steward（SS）的世界界面，它记录各个会话在做什么、PR 有没有合并、两台机器各自的状态。小猫进入小镇后，身份不变：

> **小猫是小镇里的进度秘书。它读事实、用白话讲给你听；它不接手任务，也不写代码。**

分工：

| | 小镇（SS） | 小猫 |
| --- | --- | --- |
| 负责 | 记录事实：会话、PR、设备、工作是否已处理 | 讲解和提醒：晚报、开工提醒、每周进度、发现矛盾 |
| 写什么 | 自己的事实状态 | 只写自己的解释，放在小镇的独立解释区 |
| 不做 | — | 不改小镇的工作状态，不替用户确认「已完成 / 已合并 / 已安装」，不接手任务，不写代码 |

做法：

1. **先不推倒重来。** 小猫现有的采集和晚报照常运行。
2. **接入小镇后改读小镇的事实。** 小镇的只读事实接口（SS 方案中的 P6，小猫一侧为 P6b）可用后，小猫的两项数据改从小镇读取：PR 是否已合并（解决压缩合并误判），以及另一台机器的状态（补上「MacBook 上没推送的工作看不到」）。在此之前，误判问题先在小猫内部修。
3. **在小镇里显示。** 晚报、明天从哪继续、每周进度在小镇中以小猫的解释呈现，点开可回查依据。写作规则沿用第三节。
4. **模型只用本机获准模型**，失败时保留事实和规则版文字，不影响小镇运行。

需要在 SS 一侧同步调整的地方（由 SS 仓库自行处理）：小镇演示数据把小猫写成在写代码的会话，工作状态的「接手人」提示以小猫为例。这两处与本定位不一致。
