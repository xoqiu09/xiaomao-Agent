# 小猫 Agent 重设计方案

小猫负责整理可信的项目上下文、保存任务进度和交付记录，让用户在 Codex、Claude Code 之间切换时快速继续工作。每日总结使用同一份证据；个人任务执行通过独立适配器逐步接入。

第一版沿用 Python、SQLite、Ollama 和 SwiftBar，采用“现有采集器加上下文与协调层”的路线。先在两个个人项目验证收益，再扩展执行能力。

设计日期：2026 年 10 月 14 日。时间采用 Asia/Taipei。本文中的新增接口、状态和验收目标属于候选设计；现有功能与现场记录另行标明。

## 产品目标与第一版使用方式

用户希望同时获得项目交接、每日总结、个人任务执行三项能力，实施顺序为交接、总结、执行。

| 使用时刻 | 小猫提供的结果 | 收益验收 |
| --- | --- | --- |
| 开始或接续项目 | 当前目标、最近变化、已验证结果、未核实项、下一步，以及资料对应的代码版本 | 使用者在 60 秒内判断从哪里继续；无需重新整理多份聊天 |
| 切换 Codex 或 Claude Code | 可复制的接续说明与来源清单；对过期或冲突资料明确提示 | 接手者不需要再次询问已记录的目标、工作目录和验证状态 |
| 晚间回顾 | 最多五项值得关注的变化、进行中任务、阻塞与建议动作 | 2 分钟内读完；只为需要关注的状态变化提醒 |
| 执行明确的个人任务 | 有执行目录、边界、验收方式的任务；过程可中断，结果可检查 | 改动保留、重复派发被拦截、执行结束与验证通过分别记录 |

上述时间是试点目标，需测量验证。小猫不能从 Git 推断完整的用户意图，也不能把提交、进程退出或 Agent 的口头声明提升为完成证据。

菜单以“继续项目”“今日变化”“需要处理”“任务进度”为主要入口。没有任务目标时提示补充一句目标；没有模型时仍展示规则事实。技术信息、代码片段和引用放在“查看依据”中。

## 架构选择

| 路线 | 优点 | 代价 | 决定 |
| --- | --- | --- | --- |
| 继续完善现有观察员 | 改动少，容易修复采集和日报问题 | 用户意图、接续入口和执行记录仍需补足 | 保留采集与证据部分 |
| 增加上下文与协调层 | 复用已有事实，支持统一交接、总结和任务记录 | 需要任务协议、持久化状态及统一写入管理 | 第一版采用 |
| 迁移到通用 Agent 核心 | 可获得对话、工具和渠道框架 | 需重做事实校验、个人项目边界与迁移；增加维护成本 | 第一版不迁移 |

nanobot 提供模块解耦参考；OpenClaw 提供任务通道与并发管理参考；LangGraph 提供检查点与恢复参考；Hermes 提供精简记忆与按需技能参考；Aider 提供局部代码关系参考。第一版吸收机制，不增加完整框架依赖。模型评测先复用现有入口；需要跨模型对比界面时再使用独立的 Promptfoo 工具。

### 五个职责层

| 层 | 负责的事情 | 接口边界 |
| --- | --- | --- |
| 事实采集 | 确认来源与范围，采集版本、变化、覆盖及读取错误 | 使用现有 scope、collect、change_evidence 和 store；不调用模型 |
| 项目上下文 | 将目标、规则事实、模型解释、验证结果组织成接续材料 | 输入是冻结的授权证据与任务记录，输出带版本的上下文快照 |
| 本地协调 | 管理任务、重试、预算、发布和通知 | 任务状态在本地持久化；不依赖 Codex 聊天持续可用 |
| 执行适配器 | 在指定独立工作树执行已授权任务，返回产物与验证证据 | 手动接续适配器先上线；自动调用 Claude Code、Codex 后续逐个验收 |
| 展示与同步 | SwiftBar、CLI、交接导出、可选 Notion 同步 | 只展示已发布版本；同步失败不影响本地上下文可读 |

共同的数据流为：授权来源 → 不可变证据 → 上下文快照 → 接续说明或日报 → 可选同步。任务执行使用已绑定版本的上下文，结果回到证据层，经验证后进入下一版上下文。

### 事实与意图分别保存

- 事实库 `xiaomao.sqlite` 继续保存观察与来源。只读入口使用只读连接，初始化和迁移由显式写入口执行。
- 新增 `coordination.sqlite` 保存任务规格、执行尝试、任务状态、用户决策、通知及同步账本。第一版 schema 版本为 1；这些表不写进业务仓。
- 用户目标和明确决策来自用户录入或已确认任务记录。Agent 提出的目标、结论和下一步保留作者与时间，默认标为建议或待核实。
- 本地模型只生成解释和建议；程序决定范围、时效、任务状态及验证状态。历史说明和上一版摘要不能替代当前代码证据。
- 优先按项目、时间、符号和关键词找回已有证据。第一版不增加向量数据库，也不读取完整聊天历史。

## 项目上下文与交接接口

### 接续材料的固定内容

每个项目首先显示当前目标、最近三项重要变化、进行中任务、已验证结果、待核实项和一项建议的下一步。目标未知时明确留空；建议不能自动成为执行任务。

上下文同时携带项目与工作树身份、分支、完整 HEAD、变更指纹、授权范围、观察 ID、采集截止时间、生成时间和证据引用。模型名称与提示版本作为解释来源保存，不作为事实来源。

覆盖状态分为三个互相独立的维度：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `collection_coverage` | complete / partial / unknown | 有无采集失败、首次基线或时间空档 |
| `content_coverage` | full / bounded / unavailable | 代码证据是否截断或不可读取 |
| `interpretation_state` | rule_only / queued / model_validated / failed | 有无通过结构及引用检查的模型解释 |

`model_validated` 只说明结构与引用检查通过；解释是否准确另由真实模型评测和人工抽查判断。界面将这些值转换成普通中文。

### 新增候选命令

以下命令为待实现接口，不代表当前 CLI 已支持：

```text
xiaomao context show --project ID [--json]
xiaomao context refresh --project ID [--with-model]
xiaomao context export --project ID --agent claude-code|codex --out DIR
xiaomao tasks create --spec FILE
xiaomao tasks show --id ID [--json]
xiaomao tasks checkpoint --id ID --file FILE
xiaomao tasks attach-result --id ID --file FILE
xiaomao tasks verify --id ID
```

`show` 仅读取并校验已发布资料，不扫描、不推理、不迁移数据库。`refresh` 显式请求授权范围内采集并先发布规则版，模型解释后台完成后增加版本。`export` 仅读取当前资料；陈旧、范围改变或最近采集失败时拒绝生成正常接续包，返回明确原因。

P1 先实现规则版 show、refresh、export，以及任务规格录入、checkpoint 与结果导入。`--with-model` 的后台解释在 P2 接入协调器后启用。TaskSpec 采用版本化 JSON；P1 必填项目、目标、授权来源、工作树及验收方式，task ID 在未指定时生成 UUID。仅导入 Agent 声明的结果保持待核实；`verify` 只执行 TaskSpec 已明确登记且适合当前改动的验证，原始命令、退出码、产物 hash 与来源指纹共同形成验证证据。

新命令返回码统一为：0 可用或请求已接受，2 尚无资料，3 陈旧、冲突或未核实，1 执行错误；异步请求返回 job ID，不把返回 0 写成任务已完成。现有命令的返回码保持原契约。

导出目录使用四类记录：

- `TASK.md`：目标、范围、验收方式、任务版本；没有任务时注明这是仅供阅读的项目上下文。
- `HANDOFF.md`：已验证、未验证、决定、阻塞和下一步，附引用。
- `STATE.json`：协议版本、项目身份、工作树、HEAD、变更指纹、范围 hash、观察与快照 ID。
- `evidence/`：经筛选的依据清单、结果与有界片段。默认不复制整仓、密钥、原始聊天或用户私人补充。

接手前先核对 STATE 与现场。手动导出不派发任务、不取得写入权。可读的交接与可执行的任务是两个独立状态。

### 发布与兼容

上下文快照包含 `schema_version`、`snapshot_id`、`scope_hash`、`source_fingerprint`、`intent_revision`、`observation_ids`、上述三类状态、`claims` 和 `suggested_next_actions`。每个事实性 claim 都引用证据；意图与建议携带独立来源类型。

每版产物放入不可变版本目录，全部写完并校验后原子更新当前版本指针。正文、依据、菜单和状态必须引用同一个 snapshot ID。模型解释版继承相同证据指纹；来源变化时重新生成，不覆盖旧版事实。

新上下文使用实际授权的有效工作树集合形成独立 scope hash，不修改旧交接的 registered-scope 定义。默认沿用 660 秒时效；新范围中的单棵树失败不能借用其他树的成功时间。

## 调度与恢复设计

### 第一阶段保持小型改动

先修复读写入口和事务范围，并让所有候选数据库写入口遵守同一写锁；锁竞争时写入有界本地事件文件，不能为了记录“未取得锁”再次走初始化写入口。事件文件由后续成功写入者按 event ID 幂等导入。

数据库事务只用于提交已采集的批次，模型、Git 命令、文件生成与外部网络操作均在事务之外执行。旧观察序列和 A→B→A 的重复出现语义保持不变。

这个阶段先完成可手动刷新的上下文与导出，不要求重写全部后台运行器。数据库锁定原因须用合成仓和临时 home 复现后，确定必要的最小修复。

### 第二阶段统一本地协调

后台模式采用一个 Python 协调进程。CLI 写入原子请求文件；协调进程处理请求、持久化事件及数据库写入。采集子进程只返回已筛选事实，模型子进程只读取冻结输入并返回结果；它们不直接写事实库或任务库。

协调进程内按资源分开任务通道：事实采集、上下文与日报、模型解读、外部同步。模型通道并发为 1，采集先保持并发 1，模型或网络等待不能阻塞下一次采集。写入仍只有一个拥有者。

收集健康指标后才考虑提高采集并发。统一协调入口正式接管时，旧扫描、日报写入口转为提交请求或停止重复触发，不让两套写入者共享同一 home。手动离线模式先取得同一进程锁；协调进程存活时不得绕过。

- 保留五分钟轻量采集与 21:30 日报窗口；日报先发布规则版，再增补模型解释。
- 有证据变化且缓存未命中时才创建模型任务。缓存键包含模型、提示版本、范围、背景与证据；批内模型短暂保留的策略需与现状对比后启用，批次结束释放。
- 模型仍采用既有配置及本地模型，不下载新模型、不切云端；每项目总推理预算先沿用 180 秒，唯一一次修复也计入该预算。
- 外部同步消费明确的 READY 状态，按项目与来源版本去重；保留 Notion 手工区。无变化不需要新的内容生成任务。
- Notion 桥接作为可选外部通道。即使 Codex 或 Notion 离线，本地快照、日报和任务记录仍可读。既有六项目同步范围单独保留。

本地作业状态为 queued → running → succeeded / failed / deferred，保存输入 hash、尝试次数、阶段耗时与已发布版本。重启后只有已确认退出的只读采集或解释作业可以重试；执行作业按下面的写入权规则处理。

瞬时失败单次自动重试；仍失败则至少延后十分钟。三次连续失败进入十五分钟冷却并记录恢复条件。错误首次出现、严重程度变化和恢复时各提醒一次；相同错误不反复通知。

通知保存 queued、attempted、sent、failed 等发送状态；sent 不代表用户实际看见。日报增补解释不重复发送整份日报提醒。

## 个人任务执行设计

### 执行边界

小猫的观察模型继续没有 shell 或业务写入工具。任务协调程序根据已授权 TaskSpec 调用执行适配器；观察器发现问题只能形成建议。

TaskSpec 至少记录：task ID、规格版本、用户目标、明确授权的个人项目与写路径、指定工作树与起点指纹、执行器、验证方式、停止条件、预算、禁止操作。用户修改范围或验收方式后产生新规格版本，旧授权不自动覆盖新增操作。

第一阶段执行适配器为手动导出与结果导入。随后先实现 Claude Code 自动适配器，再实现 Codex 适配器；每个都须单独验证 CLI、认证、目录限制、取消与实际任务启动。当前本机能定位到两个 CLI 文件，但这不证明自动适配器可用。

初次自动执行只使用合成个人仓库里的输入校验任务和已有针对性测试，时间预算十五分钟。真实业务试点后续单独登记；代码执行不得自动延伸为推送、部署、链上操作或处理公司材料。

### 状态与写入权

任务状态为 draft → ready → running → needs_review → verified；并有 paused、failed、cancelled。ready 表示规格完整且授权已记录；verified 表示完成规定验证并取得结果验收记录。

派发次数、实际启动回执、执行结果、验证结果和用户验收分别保存。进程退出 0 或 Agent 声称完成只允许进入 needs_review。

同一工作树只有一个执行写入者。使用操作系统排他锁配合持久化 owner、attempt ID、进程身份和 lease；到期不能单独证明旧进程停止。旧执行器已退出且不会自动重试后才能移交。无法确认进程身份时转人工处理，不自动抢占。

每个 checkpoint 保存工作树、HEAD、暂存与未暂存变更指纹、已做步骤、决定、阻塞及下一步。检查点不自动提交或隐藏已有修改。旧 attempt 的迟到结果保留为历史，不能推进当前任务状态。

Claude Code 与 Codex 间切换先导出同一任务协议，再核对现场和写入权；失败结果及修改保留。第一版只做单任务接续，不建设多 Agent 并行调度。

| --- | --- | --- |
| P0 可靠性基础 | 复现锁竞争；拆开只读与初始化写入口；缩短事务；采集失败和三类覆盖状态可定位 | 合成环境能复现原问题；修复后正常树继续工作，错误可见，旧证据没有被提升为新成功 |
| P1 项目接续 | 项目上下文、目标与任务记录、规则版刷新、SwiftBar 入口、手动导出与导入 | 两项目七天试点证明接续减少整理；导出资料能用于一次真实 Claude Code 与 Codex 双向手动接续 |
| P2 日报与协调 | 统一作业状态、分阶段耗时、模型串行、规则版先交付、外部同步恢复 | 中断恢复、模型离线、同步离线及三条调度去重验收通过；日报与菜单版本一致 |
| P3 受控执行 | 独立工作树、执行写入权、Claude Code 与 Codex 适配器、结果验证与恢复 | 合成任务中断后可接续，重复派发和双写被拦截；结果与验证证据可审查 |

P1 试点选择小猫自身与 xiuqiu-site，只读观察实际登记的个人工作树。先使用临时 home 的合成样例；个人试点采用独立数据 home，按明确的两项目配置建立新基线，不复制正式数据库或历史正文。

试点记录首次人工整理耗时，再记录至少十次有真实工作背景的接续：中位整理耗时目标降低 50%，每次目标、来源版本和验证状态都能核对。收益未达到时先调整入口或收缩范围，不继续堆叠执行能力。

### 必须覆盖的测试场景

1. 读写隔离：连续只读查询不迁移、不改观察时效、不调用模型；锁竞争记录不再次争抢初始化写锁。
2. 证据正确性：同文件连续编辑、改动撤回、多工作树矛盾、提交后 clean、授权撤回、路径替换、首次基线、时间空档和内容截断分别呈现。
3. 上下文版本：半写产物不发布；旧菜单不会配新正文；来源变化、最后采集失败与过期导出均被发现。
4. 恢复与幂等：在采集提交、模型返回、产物发布和外部同步前后分别中断；成功步骤复用，未完成部分恢复，通知不重复。
5. 模型效果：复用评测框架，增加至少二十个合成个人项目的上下文与功能变化样例；检查方向颠倒、关键遗漏、无引用断言和错误宣称完成。分别记录规则降级、结构通过和语义正确率。
6. 执行接续：适配器启动失败、额度不足、进程身份未知、旧进程仍活跃、迟到回执、暂停后接手；双写和未经授权的执行均被拦截。

真实模型评测在已安装模型中进行，不下载模型。合成样例里重大事实错误目标为零，正确且有用的解释比例目标至少 80%；结构检查不能替代人工标准答案。记录输入量、加载与推理耗时、内存和 swap，未测项目保持待测。

每阶段运行仓库已有隔离验收，并补充该阶段的真实行为回归。正式 home、外盘身份、模型质量、提醒可见性和多日稳定性各自记录；未执行项目保持 `NOT_RUN`，不能互相替代。

### 发布与回退

候选代码只在优化目录实现。保留源码差异、测试结果和当前入口清单；本地候选、提交、推送、安装切换、正式验收分别交付。

安装切换前备份正式 plist、SwiftBar 链接、配置和数据库。切换协调入口时先确认旧写入进程停止。新 schema 采用增量迁移，旧版本读取不兼容时回退到备份的数据 home；不得直接让旧程序继续写入新库。

P1 不切换现有定时任务；P2 在候选验收后才接管扫描和日报。Notion 定时任务的改动另行列出，在新通道证明能保持手工区与基线之后再切换。本文不包含实际安装或调度变更。

## Claude Code 第一轮任务

第一轮范围为 P0 和 P1 的合成环境最小闭环：复现锁竞争、实现只读上下文、明确目标录入、手动刷新与导出，交付改动和验收证据。先做到不用模型也能提供正确的接续材料，本地模型后台增补在 P2 实施。

接手前重新核对优化目录身份和 AGENTS.md。现场记录是输入，锁定原因和适配器能力仍需独立验证。已有功能满足要求时记录复用，不通过人为制造失败证明新实现必要。
